如何从零开始撸一个自己的网站

发表于2026-11-19|更新于2026-11-19|随笔
|浏览量:

我怎么用 AI 从零撸了一个免费的静态个人博客

以我自己的这个小站为例，聊聊我是怎么在 AI 帮忙下，从“啥也没有”到把一个能写、能发、能手机看、还能加密日记的静态博客跑起来的。
文笔尽量不端着，想到哪写到哪，但步骤和坑都会尽量写细，方便以后自己或别人照着来。

先说结论：为啥选“静态 + 免费”

一开始的目标其实很朴素：

  • 想有个自己的地方，放我写的小工具、推荐的软件，还有一些随手记的东西
  • 不想花钱买服务器，也不想折腾备案、数据库、后台运维
  • 最好内容在自己手里，哪天不想用了也能整包带走

所以最后选的是静态博客路线：

  • 文章写成 Markdown，本地生成一堆 HTML/CSS/JS
  • 托管到 GitHub Pages，免费、稳定、带 HTTPS
  • 没有数据库、没有后端，速度快、维护成本低

代价也很明显：动态功能（评论、在线后台、实时统计之类）要么没有，要么得靠第三方服务。对我这种“自己写、自己看、偶尔分享”的需求来说，这个取舍完全能接受。

我这个站现在长什么样

部分 我用的东西 说明
静态站点框架 Hexo 7 Node.js 生态的静态博客生成器，插件多、资料多
主题 hexo-theme-butterfly 5 好看、功能全，配置项很多，改外观比较省事
文章格式 Markdown + 顶部 --- front matter 标题、日期、分类、标签、封面之类都写在开头信息里
托管/发布 GitHub（私有源码仓库 + 公开 Pages 仓库） 源码放私库，构建产物发到 用户名.github.io
自动构建 GitHub Actions 推送源码后自动 hexo generate 并部署
加密 hexo-blog-encrypt 只给“随记”板块用，给单篇文章加密码
搜索 hexo-generator-searchdb 生成本地搜索索引 /search.json
写作方式 自己做了个本地写作台（Node 服务 + 网页） 不用记命令、不用敲 git，浏览器里写完点发布

线上地址是 GitHub Pages 默认域名那种 https://用户名.github.io/（没买域名，够用）。

从零开始我是怎么搭起来的

下面是大致顺序。跟着 AI 一步步做的时候，中间其实来回改过很多次，但主线基本就是这条。

1. 准备环境

  • 装 Node.js（Hexo 跑在 Node 上）
  • 有个 GitHub 账号
  • 装 GitHub CLI（gh） 并登录（后来写作台发文章要用它拿凭据/调接口）

小提醒：我这台电脑上 gh 装了但没加到 PATH，后来脚本里专门做了“去常见安装位置找 gh”的兼容，不然会一直报找不到。

3. 换主题、做基础配置

默认主题能用但不太合我胃口，后来换成了 Butterfly：

配置思路上有个很重要的习惯（AI 反复提醒我才记住的）：

  • 站点主配置改 _config.yml（站点名、语言、时区、URL、永久链接、搜索插件配置、加密插件文案等）
  • 主题配置尽量写在根目录的 _config.butterfly.yml 里做“覆盖”，不要去改 node_modules/hexo-theme-butterfly/ 里面的文件
    原因很简单：一旦 npm install 或升级主题，node_modules 里的改动就没了。

比如导航菜单、配色、深色模式、搜索开关、头像横幅、注入自定义 CSS，都是在 _config.butterfly.yml 里配的。

4. 规划内容结构（别一上来就乱发）

我把内容分成了三个“板块”（其实就是分类 + 导航）：

板块 用途 备注
我的软件 自己写的小工具 文章模板里带版本号、平台、下载、更新日志
推荐软件 安利别人的好东西 偏静态介绍，不追版本
随记 日常记录 只有这个板块允许加密码

还定了几个规矩，后面省了不少麻烦：

  • 文章网址用 /posts/<slug>/，slug（英文地址）一旦发布就别改，不然旧链接全废
  • 图片按文章分目录放：source/images/uploads/<slug>/...，避免不同文章同名图片互相覆盖
  • 下载文件放 source/downloads/（平铺目录），文件名一定要带版本号，不然容易覆盖

5. 把站点“免费发布”到 GitHub Pages

我用的是“双仓库”思路：

  • 私有仓库：放源码（文章、配置、主题配置、脚本、写作台等）
  • 公开仓库：wawel114/wawel114.github.io，只放构建出来的静态文件，给 Pages 用

发布流程是：

  1. 本地把源码提交到私有仓库
  2. GitHub Actions 自动执行：装依赖 → hexo generate → 把 public/ 推到公开仓库的 Pages 分支
  3. 几十秒到一分钟后，线上就更新了

Actions 里核心就几步（简化理解）：checkout、setup-node、npm ci、hexo generate，然后用 peaceiris/actions-gh-pages 把 ./public 发布出去。公开仓库那边需要配置好 deploy key/权限，Pages 指向对应分支。

一开始图省事想本地直接搞，但后来为了“换电脑也能写、手机也不指望但至少流程简单”，还是把构建交给云端了。事实证明很香。

6. 做一个“本地写作台”（解放双手）

说实话，纯命令行写博客也不是不行，但我懒，而且容易忘步骤。于是让我跟 AI 一起整了个本地写作台：

  • 双击 tools/writer-start.bat 启动一个本地 Node 服务
  • 浏览器自动打开 http://127.0.0.1:5173
  • 页面上可以：选板块、填标题/slug、写正文、拖图片、传下载文件、给随记加密码、管理/删除文章、改站点设置（横幅头像标题之类）
  • 点“上传到云端”就走发布流程；平时保存只写本机文件，不点发布不会把半成品弄上线

这个写作台只监听 127.0.0.1，局域网别的设备访问不到，安全感好一点。

这里有个关键取舍： 我的环境一开始没有 git、而且 PowerShell 默认禁止跑 .ps1 脚本。
所以发布和一些自动化逻辑最后都做成了 Node 脚本（比如 tools/gh-sync.js、tools/writer.js），通过 GitHub 接口/gh 来同步，而不是依赖本机 git 命令；批处理里也是调 node xxx.js。这套“绕开限制”的方案，回头看反而挺适合我这台电脑。

7. 一点点打磨体验

后面就是典型的“用着用着发现哪不顺眼就改”：

  • 配了本地搜索，并且加了过滤：带密码的文章不进搜索索引（不然标题摘要可能泄露）
  • 开了深色模式、图片懒加载，字体用系统字体，不额外拉网络字体
  • 调了粉色系主题色（也顺手在配置里留了别的配色备注）
  • 写了自定义 CSS（source/css/custom.css）专门修手机端显示
  • 做了文章删除的双向同步：本地删了，发布时云端也跟着删，不会“删了还在”
  • 给自己和“未来接手的 AI”写了文档：docs/MANUAL.md、docs/HANDOFF.md，还专门搞了一篇站内的《本站功能更新日志》，约定好以后每次改动怎么记

开发过程中踩过的坑

这部分才是精华，建议认真看，能少掉不少头发。

1. gh 明明装了却找不到

  • 现象：脚本里调 gh 报“不是内部或外部命令”
  • 原因：GitHub CLI 不在 PATH（我这台机器就是装在 C:\Program Files\GitHub CLI\gh.exe）
  • 解决：发布/同步逻辑里做了兜底，PATH 找不到就去常见安装路径找；必要时直接用绝对路径

2. Node 请求 HTTPS 报错 / fetch failed

  • 现象：本地跑发布相关脚本时网络请求失败
  • 原因：环境里证书链问题
  • 解决：运行 Node 脚本时加 --use-system-ca（用系统证书）

3. PowerShell 不让跑 .ps1

  • 现象：执行策略是 Restricted，脚本直接被拦
  • 解决：少写/不依赖 .ps1，把逻辑放进 .js 或 .bat 里调用 Node

4. 手机上看横幅图“只露中间一条”

  • 现象：桌面端挺好，手机竖屏一看，顶部大图被裁得妈都不认识
  • 原因：主题默认 background-size: cover + 很高的 header（首页接近满屏），竖屏容器比例和横幅图比例差太多，只能裁中间
  • 解决：在 source/css/custom.css 里针对小屏改成 contain 让图完整显示，下面用主题色补一条色带放标题；首页、文章页、归档/分类页分别调高度。这样换图也不用改 CSS，不管横幅什么比例都不怕被裁。

5. 手机端表格挤成“一列一个字”

  • 现象：中文表格在窄屏下被硬挤，字竖着排，没法看
  • 解决：给文章内容里的表格设置一个合理的最小宽度，让它在小屏上可以横向滚动（主题本来就有 .table-wrap 的滚动能力，配合一下就好）

6. 加密文章“看起来加密了，其实没完全藏住”

这个坑是认知上的：

  • hexo-blog-encrypt 加密的是正文内容，但标题、日期、分类、链接通常还是公开可见的
  • 我额外做了搜索索引过滤（带密码的不进 search.json），但归档/分类页里标题是否露出还得看主题和后续处理
  • 密码是写在文章源文件里的（会进私有源码库），所以“私密”是相对的：别用你别处的重要密码

说白了：适合防路人手滑点开，不适合存真正的机密。

7. 图片/附件一删，线上还在

  • 现象：本地删了文章，网站上还有
  • 原因：以前发布可能只做“增量上传”不处理删除；而且我理解成“删了本地就完事”
  • 解决：把同步做成双向（在受管范围内），本地删了的文件发布时云端也删；同时明确“点上传才生效”。
    另外文章删除时，文章自己的图片目录会一起删，但 source/downloads/ 是公共下载目录，后来又加了逻辑：只自动删“没被其他文章引用”的附件，避免误伤共用文件。

8. downloads/ 平铺目录的覆盖风险

  • 现象：两篇文章都传 tool.zip，后传的把前面的覆盖了
  • 原因：下载目录没按文章分子文件夹
  • 解决：约定文件名带版本号（比如 xxx-v1.2.0.zip）；删除时也做引用检查。要是重来一次，也许会考虑按文章分目录，但现在先靠规范+逻辑兜底。

9. 写作台改了代码但页面没变化

  • 现象：我明明改了 tools/writer.js / writer-ui.html，浏览器里行为还是老的
  • 原因：写作台服务进程还在跑，内存里是旧代码
  • 解决：关掉写作台窗口重新启动（必要时确认端口没被旧进程占着）

10. 网站“看着不快”，尤其手机

  • 现象：图片加载慢；另一个 AI 在改文件时更慢
  • 原因：
    • 有几张封面图特别大（我后来发现两张 cover 是 2MB+ 的 PNG）
    • 本地用 hexo server 预览时，它会监听文件变动自动重建，AI 一顿保存就疯狂触发重建
  • 解决：把大图压缩成合适尺寸的 JPG/WebP；平时“只看不改”就先 hexo generate 再用静态方式预览，别一直开着 watch 模式被反复构建拖慢

11. 生成/发布时终端中文乱码（Windows 老问题）

  • 现象：日志里中文显示成一坨问号或奇怪字符
  • 影响：不影响功能，但看着难受、排错费劲
  • 处理：能确认关键字（success/error/文件名）就行；必要时看生成后的文件或浏览器页面验证，别太依赖终端那一屏

一些容易被忽略的小事实（挺重要）

  • “免费”主要指托管和框架：GitHub Pages、Hexo、主题都不花钱；但你的时间、以及以后可能想买的域名不算在内。
  • 公开站点就是公开的：放进站点里的图片、zip、apk，别人知道链接就能下。别把不该公开的东西传上去。
  • 自定义样式别改主题源码：写在自己的 custom.css 里再通过主题配置注入，升级主题才不心慌。
  • 改完先本地生成/预览再发布：hexo generate 能提前抓一堆低级错误；手机和桌面都看一眼，省得线上翻车。

如果再让我从零来一次，我会怎么做

  1. 先把“内容结构和命名规则”想清楚（分类、slug 规则、图片/附件怎么放）
  2. 尽早把发布链路跑通（本地生成 → 云端构建 → Pages 上线），别等文章写了一堆才发现发不出去
  3. 主题配置从第一天就用“覆盖文件”，坚决不碰 node_modules
  4. 图片一开始就控制尺寸和格式，别等站点慢了再救火
  5. 让 AI 帮忙的同时，把关键约定写进文档（比如我后来加的 docs/ 和更新日志），不然换一轮对话/换一个 AI，很容易把之前的决定改回去

最后碎碎念

用 AI 搭这个站，最大的感受不是“它全自动帮我搞定了”，而是它很适合当一个不知疲倦的搭档：查配置、写脚本、修 CSS、定位奇怪报错、顺手补文档，这些又碎又耗时间的事，它能陪着你一项项磨过去。

但方向还是得自己把握：我要什么结构、哪些东西不能公开、哪些妥协能接受、哪些坑踩一次就够了——这些最后都得自己拍板。AI 再厉害，也不会替你记住“这个 slug 发布后不能改”“下载目录别乱覆盖”这种跟你站点强相关的规矩（所以我才把它们写进文档里）。

总之，折腾归折腾，看到自己的网站真的跑在网上、手机也能正常看、想发点什么点几下就行的时候，还是挺爽的。希望这篇流水账对以后要搞类似东西的我（或者你）有点用。
